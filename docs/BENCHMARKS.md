# BigCat: Performance & Benchmark Report (Phase 1 & Phase 2)

Comprehensive performance and allocation benchmarks for **BigCat Key-Value Storage Engine**, covering single-file, multi-file rotation, and live RESP network throughput.

---

## Benchmark Environment
* **OS:** Linux 6.8 (x86_64)
* **CPU:** AMD Ryzen 5 5600H with Radeon Graphics (6 Cores / 12 Threads @ 3.30GHz - 4.20GHz)
* **Go Version:** `go1.27.4 linux/amd64`
* **Compiler Flags:** `-benchmem`

---

## 1. End-to-End Engine Benchmarks (`bigcat`)

These benchmarks measure the complete lifecycle through the public `DB` API (`Put` and `Get`), including serialization, append-only multi-file I/O, CRC32 checksums, and in-memory `KeyDir` indexing.

| Benchmark | Operations | Latency | Memory / Op | Allocs / Op | Est. Throughput | Notes |
|---|---|---|---|---|---|---|
| `BenchmarkDB_Put` | 723,351 | **1,742 ns/op** (1.74 µs) | 144 B/op | 3 allocs/op | **~574,000 writes/sec** | Append to active file + index update |
| `BenchmarkDB_Get` | 1,486,630 | **871.2 ns/op** (0.87 µs) | 144 B/op | 3 allocs/op | **~1,148,000 reads/sec** | Single `pread(2)` + CRC check |

### Key Takeaways:
* **Over 1.14 Million Point Lookups/sec:** Random reads complete in sub-microsecond latency (871 ns) thanks to the in-memory index lookup combined with a single `pread(2)` syscall across multi-file storage.
* **Over 570,000 Appends/sec:** High write throughput to the OS page cache while calculating CRC32 checksums on every write.

## 3. Serialization & Codec Benchmarks (`internal/record`)

Measures Little-Endian binary packing, header construction, payload slicing, and CRC32 IEEE computation.

| Benchmark | Operations | Latency | Memory / Op | Allocs / Op | Est. Throughput |
|---|---|---|---|---|---|
| `BenchmarkBinaryCodec_Encode` | 19,813,900 | **55.83 ns/op** | 80 B/op | 1 allocs/op | **~17.9M ops/sec** |
| `BenchmarkBinaryCodec_Decode` (stream `io.Reader`) | 9,850,641 | **148.0 ns/op** | 200 B/op | 4 allocs/op | **~6.7M ops/sec** |
| `BenchmarkBinaryCodec_DecodeBytes` (contiguous memory) | 23,483,414 | **52.02 ns/op** | 64 B/op | **1 allocs/op** | **~19.2M ops/sec** |

### The Power of `DecodeBytes`:
* `DecodeBytes` is **almost 3x faster** than streaming `Decode(io.Reader)` because it calculates CRC32 directly across contiguous memory without an intermediate hasher interface and slices keys/values with zero extra allocations.

## 4. Storage File I/O Benchmarks (`internal/storage`)

Measures append-only file writes and stateless `pread(2)` random reads directly on disk.

| Benchmark | Operations | Latency | Memory / Op | Allocs / Op | Est. Throughput |
|---|---|---|---|---|---|
| `BenchmarkDataFile_Write` | 1,000,000 | **1,177 ns/op** (1.18 µs) | 0 B/op | **0 allocs/op** | **~849,000 writes/sec** |
| `BenchmarkDataFile_ReadAt` | 1,841,496 | **642.0 ns/op** (0.64 µs) | 256 B/op | 1 allocs/op | **~1,557,000 reads/sec** |
| `BenchmarkFileManager_Write` (with rotations) | 545,445 | **2,036 ns/op** (2.04 µs) | 0 B/op | **0 allocs/op** | **~491,000 writes/sec** |
| `BenchmarkFileManager_ReadAt` (multi-file dispatch) | 1,791,039 | **667.5 ns/op** (0.67 µs) | 128 B/op | 1 allocs/op | **~1,498,000 reads/sec** |

### Key Takeaways:
* **Lock-Free Concurrent Reads:** `ReadAt` uses `pread(2)` which bypasses the shared OS file seek pointer, executing in ~667 nanoseconds across multiple rotated immutable files.
* **Zero-Allocation Multi-File Writes:** Writing and rotating files incurs 0 heap memory allocations.

## 6. Phase 2: Multi-File Rotation Performance & Findings

Comprehensive comparison and architectural findings evaluating the transition from single-file storage (Phase 1) to multi-file rotation with immutable segment management (Phase 2):

| Evaluation Dimension | Benchmark / Condition | Phase 1 (Single-File) | Phase 2 (Multi-File Rotation) | Architectural Finding & Impact |
|---|---|---|---|---|
| **Storage Layout** | Data directory files | Single unbounded `data.db` | Segmented `00000.data` ... `0000X.data` | Bounded file sizes; unlocks zero-downtime background compaction (Phase 3) |
| **Point Read Latency** | `BenchmarkDB_Get` (in Go) | **778.3 ns/op** | **871.2 ns/op** | Sub-microsecond point reads maintained; negligible ~90ns delta for $O(1)$ file routing |
| **Point Read Throughput** | `BenchmarkDB_Get` (in Go) | ~1,285,000 ops/sec | **~1,148,000 ops/sec** | Strictly maintains the **1 disk seek / pread(2)** guarantee across all files |
| **File Read Dispatch** | `BenchmarkFileManager_ReadAt` | N/A | **667.5 ns/op** (~1.50M reads/sec) | Stateless concurrent `pread(2)` reads execute without file-pointer mutex lock contention |
| **Sequential Appends** | `BenchmarkFileManager_Write` | 1,177 ns/op | **2,036 ns/op** (~491,000 writes/sec) | 0 heap allocations; includes threshold checking and seamless rotation |
| **Concurrent TCP SET** | `redis-benchmark -c 50` | ~300 req/sec | **~80,775 req/sec** | Active file rotation seamlessly handles 50 concurrent writers with 0 dropped packets |
| **Cross-File TCP GET** | `redis-benchmark -c 50` | ~32,100 req/sec | **~86,950 req/sec** | 100% data integrity verified across 8 rotated immutable `.data` files |
| **Pipelined TCP GET** | `redis-benchmark -P 16` | ~186,100 req/sec | **~508,670 req/sec** | **>0.5 Million req/sec** over TCP; loopback network saturation |
| **Reader Disruption During Rotation** | Concurrent reads during active file rotation | N/A | **0 errors / 0 dropped reads** | Existing file descriptor handles stay open; readers experience zero interruption |
| **Cold Crash Recovery** | `KeyDir` rebuild on reboot | Single sequential scan | Ordered ascending scan (`00000` $\to$ `0000X`) | Replays all log segments in order; latest updates and tombstones overwrite stale keys |

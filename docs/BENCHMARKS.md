# BigCat: Performance & Benchmark Report (Phase 1 & Phase 2)

Comprehensive performance and allocation benchmarks for **BigCat Key-Value Storage Engine**, covering single-file, multi-file rotation, and live RESP network throughput.

---

## Benchmark Environment
* **OS:** Linux 6.8 (x86_64)
* **CPU:** AMD Ryzen 5 5600H with Radeon Graphics (6 Cores / 12 Threads @ 3.30GHz - 4.20GHz)
* **Go Version:** `go1.27.4 linux/amd64`
* **Compiler Flags:** `-benchmem`

---

## 1. End-to-End Engine Benchmarks (`bigcat`)

These benchmarks measure the complete lifecycle through the public `DB` API (`Put` and `Get`), including serialization, append-only multi-file I/O, CRC32 checksums, and in-memory `KeyDir` indexing.

| Benchmark | Operations | Latency | Memory / Op | Allocs / Op | Est. Throughput | Notes |
|---|---|---|---|---|---|---|
| `BenchmarkDB_Put` | 723,351 | **1,742 ns/op** (1.74 µs) | 144 B/op | 3 allocs/op | **~574,000 writes/sec** | Append to active file + index update |
| `BenchmarkDB_Get` | 1,486,630 | **871.2 ns/op** (0.87 µs) | 144 B/op | 3 allocs/op | **~1,148,000 reads/sec** | Single `pread(2)` + CRC check |

### Key Takeaways:
* **Over 1.14 Million Point Lookups/sec:** Random reads complete in sub-microsecond latency (871 ns) thanks to the in-memory index lookup combined with a single `pread(2)` syscall across multi-file storage.
* **Over 570,000 Appends/sec:** High write throughput to the OS page cache while calculating CRC32 checksums on every write.

## 7. Phase 2.5: High-Concurrency Write Optimizations (Lock Elision & Group Commit)

Evaluates the two-stage write path optimization:
1. **Part 1 (Lock Elision):** Moving record serialization and CRC32 IEEE computation outside `db.mu.Lock()`.
2. **Part 2 (Group Commit):** Adaptive batching of concurrent writes via `GroupCommitter` to coalesce multiple writes and physical `fsync(2)` flushes into a single I/O operation.

### A. High-Throughput Mode (`-sync=false`, OS Page Cache)
Records are encoded in parallel across multi-core CPU threads, with zero-latency opportunistic draining on the group committer:

| Benchmark | Workload | Concurrency | Latency | Throughput | Impact / Findings |
|---|---|---|---|---|---|
| `BenchmarkDB_ParallelPut` | Multi-core In-Process | 12 threads | 2,399 ns/op | **~416,840 writes/sec** | Zero mutex convoying during record encoding & CRC calculation |
| `Live TCP SET` | `redis-benchmark` | 50 clients | 0.65 ms | **~76,277 req/sec** | High-concurrency TCP throughput over loopback network |
| `Live TCP GET` | `redis-benchmark` | 50 clients | 0.65 ms | **~76,161 req/sec** | Concurrent point reads across active and immutable files |
| `Live TCP GET (Pipelined)` | `redis-benchmark -P 16` | 50 clients | 0.03 ms | **~550,505 req/sec** | Network packet batching exceeding **0.55 Million reads/sec** |

### B. Strict Durability Mode (`-sync=true`, Hardware `fsync`)
Comparing individual `fsync(2)` per write versus coalesced Group Commit under 50 concurrent client connections:

| Mode | Concurrency | `fsync` Strategy | Average Throughput | Speedup | Latency Profile |
|---|---|---|---|---|---|
| **Before Group Commit** | 50 clients | 1 `fsync` per write | **~180 – 250 req/sec** | Baseline | Constrained by ~4ms physical SSD flash latency |
| **With Group Commit** | 50 clients | Coalesced batch `fsync` | **~12,680 – 13,245 req/sec** | **~53x (~5,200%)** | 50 writes share 1 single hardware sync (~0.08ms/write) |

### C. Architectural Takeaway: Why Group Commit Works
1. **The Physical Wall:** Physical SSD/NVMe flash controllers require ~4 ms to commit dirty blocks from volatile controller cache to non-volatile NAND cells. Serializing 50 independent `fsync(2)` calls took $50 \times 4\text{ms} = 200\text{ms}$.
2. **Adaptive Coalescing:** `GroupCommitter` introduces zero artificial latency timers (`linger.ms = 0`). Under 1 client, it flushes immediately in ~0.05ms. Under 50 concurrent clients, writes naturally queue while the previous batch writes to disk, automatically coalescing all pending writes into a single disk write and single `fsync(2)`.
3. **Double Guardrails:** The batch flush is capped by both item count (`maxBatchSize = 128`) and memory buffer size (`maxBatchBytes = 4MB`), preventing oversized memory allocations while keeping the write pipeline continuously saturated.

## 8. Explicit Atomic `WriteBatch` & Redis `MSET` Benchmarks

Evaluates application-level atomic batch writes (`WriteBatch` with in-batch key deduplication and `GroupCommitter` coalescing) both in-process and over live TCP (`MSET`).

### A. In-Process `WriteBatch` Throughput (`go test -bench=BenchmarkDB -benchmem .`)

| Benchmark | Workload | Latency / Batch | Amortized Per Key | Effective Throughput |
|---|---|---|---|---|
| `BenchmarkDB_WriteBatch10` | 10 keys/batch (sequential) | 9,792 ns/op | **~979 ns/key** | **~1,021,200 keys/sec** (~124k batches/sec) |
| `BenchmarkDB_WriteBatch100` | 100 keys/batch (sequential) | 97,154 ns/op | **~972 ns/key** | **~1,029,300 keys/sec** (~10.3k batches/sec) |
| `BenchmarkDB_ParallelWriteBatch10` | 10 keys/batch (12 threads) | 11,415 ns/op | **~1,142 ns/key** | **~876,000 keys/sec** (~87.6k batches/sec) |
| `BenchmarkDB_Put` *(baseline)* | 1 key/op (sequential) | 3,046 ns/op | 3,046 ns/key | ~328,300 keys/sec |

* **Key Finding:** Batching 10–100 mutations into an atomic `WriteBatch` cuts per-key commit overhead by **~3.1x** compared to individual `Put` calls, pushing sequential embedded ingestion past **1 Million keys/sec**.

### B. Live TCP `MSET` (`redis-benchmark`, 50 Concurrent Clients, 10 Keys/Request)

| Mode | Command | Request Rate | Key Ingestion Rate | Notes |
|---|---|---|---|---|
| **Page Cache (`-sync=false`)** | `MSET` (10 keys) | **~64,350 req/sec** | **~643,500 keys/sec** | Atomic 10-key commit over loopback TCP (`SET`: ~67.2k req/sec, `GET`: ~73.7k req/sec) |
| **Strict Durability (`-sync=true`)** | `MSET` (10 keys) | **~8,382 req/sec** | **~83,822 keys/sec** | Concurrent `MSET` batches share GroupCommitter's `fsync(2)` flush |
